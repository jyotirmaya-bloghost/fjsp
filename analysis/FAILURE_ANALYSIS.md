# Failure Analysis

This document follows the structure required by the problem statement. For each
failure mode: **Observation → Evidence → Hypothesis → Structural explanation →
Proposed improvement.** Proposed improvements are ideas only; they are not
implemented, with one exception (Failure Mode 5), which was implemented because
it invalidated the measurement instrument itself.

Every number quoted here is regenerated by:

```bash
python experiments/compare_algorithms.py   # raw runs   -> experiments/*.csv
python analysis/aggregate.py               # summaries  -> analysis/summary_by_class.csv
python analysis/seed_dominance.py          # FM1 evidence -> analysis/seed_dominance.csv
python experiments/edge_cases.py           # hand-built edge cases
```

Experimental setup: 9 instance classes × 5 seeds, 10 jobs, 6 machines, 3–6
operations per job, population 40, 80 generations. For each `(class, seed)` the
instance is generated **once** and given to all three algorithms, so
comparisons are paired.

## Failure Mode 1 — The GA degenerates into an expensive greedy on four of nine classes

### Observation

On `high_flexibility`, `hard`, and `extreme`, the GA's best-so-far makespan is
unchanged from generation 0 to generation 80 in **5 out of 5 seeds**. It spends
roughly 200–400 ms of search to return precisely the solution the greedy
heuristic produced in 0.2 ms. `bottleneck_heavy` shows the same for GA
(0.00% improvement, 5/5 stagnant), with SLGA escaping in 1 seed.

### Evidence

From `analysis/convergence_summary.csv`:

| class | GA improvement gen0→final | runs with zero improvement |
|---|---|---|
| high_variance | 7.32% | 2/5 |
| low_flexibility | 6.28% | 2/5 |
| balanced | 6.10% | 1/5 |
| average | 3.84% | 2/5 |
| machine_advantage | 1.85% | 3/5 |
| bottleneck_heavy | 0.00% | 5/5 |
| hard | 0.00% | 5/5 |
| high_flexibility | 0.00% | 5/5 |
| extreme | 0.00% | 5/5 |

The cause is isolated by `analysis/seed_dominance.py`, which samples 1500 random
chromosomes per instance using the GA's own initializer and decoder, and
compares them to the greedy seed. The **dominance ratio** is
`best random makespan / greedy makespan`:

| class | mean dominance ratio | GA improvement |
|---|---|---|
| balanced | 0.87 | 6.10% |
| low_flexibility | 0.87 | 6.28% |
| high_variance | 0.95 | 7.32% |
| average | 1.04 | 3.84% |
| bottleneck_heavy | 1.24 | 0.00% |
| machine_advantage | 1.33 | 1.85% |
| hard | 1.50 | 0.00% |
| high_flexibility | 1.59 | 0.00% |
| extreme | 4.01 | 0.00% |

Spearman rank correlation between dominance ratio and GA improvement across the
nine classes is **ρ = −0.70**. (Pearson is −0.56, dragged toward zero by the
`extreme` outlier at 4.01; the rank correlation is the honest statistic here
given one extreme point and n = 9.)

Concretely, on `high_flexibility` seed 1: greedy achieves 72, while the best of
1500 random chromosomes is 116 — random search is 61% worse. On
`low_flexibility` seed 2: greedy achieves 168, best random is 142 — random
search is 15% *better* than the seed.

### Hypothesis

The population is initialized as one informed individual (decoded from the
greedy ECT schedule) plus 39 random individuals. When the greedy seed is far
better than anything random sampling produces, it dominates the population
immediately. Tournament selection then pairs the elite with much worse partners,
POX crossover of a good parent and a bad parent yields offspring worse than the
elite, elitism preserves the elite unchanged, and the best-so-far never moves.
The GA is not exploring — it is repeatedly rediscovering its own seed.

### Structural explanation

The dominance ratio is not arbitrary; it is a direct consequence of flexibility
and processing-time spread interacting with how each method assigns machines.

Greedy ECT chooses, at every step, the (operation, machine) pair with the
earliest completion time. As `machine_flexibility` rises, the eligible set
`E(j,k)` grows, so greedy has more machines to choose from and is increasingly
likely to find one that is both fast and free. Its myopia costs little, because
with many alternatives a locally good choice rarely blocks anything later.

Random machine assignment does the opposite. It draws uniformly from `E(j,k)`,
so a larger eligible set means a *higher* chance of drawing a slow machine. On
`extreme`, where `machine_advantage={1: 0.05}` makes machine 1 about 20× faster
and the time range is (1, 200) with variance 3.0, missing machine 1 is
catastrophic — random chromosomes average a makespan of ~2000 against greedy's
~300, a ratio of 4.01.

So flexibility pushes greedy and random in opposite directions, and the gap
between them widens exactly where the GA stalls. The failure is therefore not
"the GA is bad at flexible instances" — it is that **seeding a population with a
solution that random initialization cannot approach destroys population
diversity at generation 0**, and the classes where this happens are precisely
the high-flexibility, high-advantage, high-spread ones.

Note the inversion this produces: the GA helps most on `low_flexibility`
(+6.28%), the class where the routing search space is *smallest*. That is
counterintuitive until the dominance ratio is taken into account — there, greedy
is weak (gap 79.7%, the worst of any class) and random individuals are
competitive, so the population carries real diversity.

### Proposed improvement

Three ideas, in order of how directly they attack the mechanism:

1. **Seed a diverse elite, not a single elite.** Instead of one greedy
   chromosome, seed 10–20% of the population with *perturbed* greedy solutions
   (e.g. greedy with randomized tie-breaking, or greedy run with different
   dispatching rules such as shortest-processing-time and most-work-remaining).
   This keeps the population near the good region while preserving variation
   that crossover can exploit.
2. **Bias random initialization toward fast machines.** Sample machines from
   `E(j,k)` with probability inversely proportional to processing time rather
   than uniformly. This should collapse the dominance ratio on `extreme` and
   `high_flexibility` directly, and is the cheapest change to test.
3. **Diversity-preserving replacement.** Reject offspring identical in makespan
   to an existing individual, or apply fitness sharing, so the elite cannot
   occupy the whole population.

A clean experiment: re-run only the four stagnant classes with idea 2, and check
whether the dominance ratio falls below ~1.2 and improvement becomes non-zero.
The dominance ratio is a cheap predictor that can be measured *before* running
the GA, so it could also be used to decide whether running a GA is worth it at
all on a given instance.

## Failure Mode 2 — Greedy ECT is worst exactly where routing freedom is lowest

### Observation

Greedy ECT's gap to the lower bound is worst on `low_flexibility` (79.7%) and
`high_variance` (72.5%), and best on `high_flexibility` (49.0%) and `balanced`
(51.4%).

### Evidence

Greedy gap by class: low_flexibility 79.7% > high_variance 72.5% > average 57.9%
> machine_advantage 56.9% > hard 56.0% > extreme 54.2% > bottleneck_heavy 54.1%
> balanced 51.4% > high_flexibility 49.0%.

These are the two classes where the GA recovers the most (−12.1% and −10.4%
makespan respectively), confirming the greedy solutions genuinely had slack
rather than the bound being loose there.

### Hypothesis

Greedy's one-step lookahead is harmful in proportion to how irreversible each
assignment is. With few eligible machines, an early operation placed on a
contended machine cannot be routed around later; with many, later operations
have alternatives.

### Structural explanation

FJSP couples two decisions: sequencing and routing. Greedy ECT resolves both
simultaneously and irrevocably using a single myopic criterion. Under low
flexibility (`machine_flexibility=0.15`, so ~1 eligible machine per operation on
6 machines), routing is nearly forced, and the makespan is determined almost
entirely by *sequencing* — the order in which jobs claim their few shared
machines. Greedy never revisits that order, so a poor early sequencing decision
propagates through every downstream operation on that machine.

Under `high_variance` (range (1,50), variance 2.0) the mechanism is different.
ECT minimizes completion time, so it systematically prefers short operations
first and defers long ones. Long operations therefore tend to be scheduled late,
where they cannot be overlapped with anything and land directly on the critical
path. This is consistent with the GA recovering 7.32% there purely by reordering
— the largest convergence gain of any class.

### Proposed improvement

Replace the single ECT rule with a small portfolio (ECT, shortest processing
time, most work remaining, longest processing time first) and take the best
result per instance. On `high_variance` specifically, a longest-processing-time-first
rule should schedule long operations early where they can overlap. This is cheap
(each rule is one pass) and would give the GA a stronger and more varied seed
set, which also addresses Failure Mode 1.

## Failure Mode 3 — SLGA converges earlier but frequently lands slightly worse than fixed GA

### Observation

The adaptive controller does not reliably beat the fixed-parameter GA. SLGA is
worse on `average` (95.4 vs 95.2), `low_flexibility` (127.4 vs 125.4) and
`balanced` (105.4 vs 104.6); better on `machine_advantage` (82.6 vs 84.8),
`high_variance` (306.0 vs 308.8) and `bottleneck_heavy` (90.2 vs 91.0).

### Evidence

Mean generation of last improvement (`analysis/convergence_summary.csv`):

| class | GA | SLGA |
|---|---|---|
| average | 35.6 | 12.2 |
| low_flexibility | 32.8 | 18.6 |
| balanced | 35.6 | 31.4 |
| machine_advantage | 18.2 | 13.0 |
| high_variance | 36.2 | 30.2 |

SLGA stops improving earlier than GA in every class. On the three classes where
it finishes worse, the difference in stopping generation is largest (average:
12.2 vs 35.6). Aggregated over all 45 paired runs, SLGA beats GA in 8, ties in
most, and loses in several — no consistent advantage.

### Hypothesis

The Q-learning/SARSA controller is rewarded primarily for improvement in the
best makespan. Early in a run, raising selection pressure (or lowering mutation)
produces immediate best-fitness gains, so the controller learns to do that. This
buys short-term progress at the cost of diversity, and the run converges
prematurely.

### Structural explanation

The controller's state is a weighted scalar (0.35 average fitness, 0.35
diversity, 0.30 best fitness) mapped to 20 discrete states, with 9 actions and a
20×9 Q-table — 180 entries to learn within a single 80-generation run. There is
no cross-run learning: each run starts from an empty table. Eighty generations
is simply not enough experience to populate 180 state-action values, so the
controller behaves close to randomly for much of the run and its reward signal
is dominated by short-horizon best-fitness improvements. That combination —
noisy policy plus a myopic reward — is what produces "faster but slightly worse".

This is an honest negative result: the added complexity of the RL controller is
not paying for itself at this problem size and generation budget.

### Proposed improvement

1. **Persist the Q-table across runs** within a class, so learning amortizes over
   many instances instead of restarting at zero each time.
2. **Add a diversity term to the reward** (or penalize diversity collapse), so
   the controller is not rewarded purely for short-term best-fitness gains.
3. **Shrink the state/action space** (e.g. 5 states × 3 actions = 15 entries),
   which is far more learnable in 80 generations.
4. Test at a larger generation budget (400+), where the current table has a
   realistic chance of converging — the fair comparison is whether SLGA's
   advantage appears when it has enough experience to learn anything.

## Failure Mode 4 — More than half the search budget produces nothing

### Observation

Across classes where the GA improves at all, the last improving generation
averages 18–36 out of 80. The remaining generations change nothing.

### Evidence

`last_improving_generation` for GA: average 35.6, low_flexibility 32.8, balanced
35.6, high_variance 36.2, machine_advantage 18.2 — all out of 80 total
generations. On the four stagnant classes it is 0.0, meaning 100% of the budget
is wasted there.

### Hypothesis

Once the population loses diversity (Failure Mode 1's mechanism, in milder
form), crossover between near-identical parents is effectively a no-op and only
mutation can make progress — at too low a rate to matter.

### Structural explanation

POX crossover copies a subset of jobs' positions from one parent and fills the
rest from the other. When both parents share most of their operation sequence,
the offspring is a near-copy of both. The search then relies on a single swap or
machine-reassignment mutation to find an improvement, and in a solution space of
roughly `(total_ops)!` orderings times the product of eligible-set sizes, a
single random swap almost never improves an already-decent schedule.

### Proposed improvement

Add a restart or stopping criterion: if the best-so-far has not improved for
~20 generations, either stop (saving ~55% runtime at no quality cost) or
re-inject randomized individuals to restore diversity. The former is a free
efficiency win and easy to justify from this data; the latter directly targets
the diversity collapse.

## Failure Mode 5 — The lower bound was too weak to measure anything (fixed)

This one was found while auditing the metrics rather than the algorithms, and it
is included because it invalidated every gap number previously reported. Unlike
the others, it **was** implemented, because leaving it unfixed would mean all the
tables above were measured with a broken instrument.

### Observation

The hand-built `single_machine` edge case reported a 200% gap. But with exactly
one machine, every operation must run on it, non-preemptively, so the optimal
makespan is provably the sum of all processing times. The greedy schedule was
already optimal and the metric was reporting it as three times worse than
necessary.

### Evidence

Edge-case gaps before and after the fix:

| edge case | gap (old bound) | gap (new bound) |
|---|---|---|
| single_machine | 200.0% | **0.0%** |
| identical_times | 100.0% | **0.0%** |
| many_short_ops | 340.0% | 29.4% |
| bottleneck_machine | 300.0% | 140.0% |
| machine_advantage_edge | 300.0% | 166.7% |
| near_zero_flexibility | 100.0% | 42.9% |
| extreme_time_gap | 200.0% | 50.0% |
| near_total_flexibility | 50.0% | 50.0% |
| long_critical_chain | 6.2% | 6.2% |
| one_job | 0.0% | 0.0% |

Two cases are now proven optimal rather than appearing badly suboptimal.

### Hypothesis / structural explanation

The original bound (LB1) was purely precedence-based: for each job, sum the
minimum processing time of its operations; take the max over jobs. This is valid
but ignores machine contention entirely. It answers "how fast could the longest
job finish if it had the machines to itself?" — which says nothing at all when
the binding constraint is machine capacity rather than chain length.

The added bound (LB2) is a work-content argument: every operation must occupy
some machine for at least its fastest eligible time, so total unavoidable work is
`Σ min_m p(j,k,m)`. That work runs on at most `m` machines in parallel, so some
machine is busy for at least `total/m`, giving `C_max ≥ ⌈total/m⌉`. It assumes
the most optimistic case on all three counts simultaneously (every operation on
its fastest machine, perfect load balance, zero idle), so no feasible schedule
can beat it.

The reported bound is now `max(LB1, LB2)`. Neither dominates: LB2 is stronger on
machine-constrained instances (26 of 45 generated instances), while LB1 remains
stronger on `extreme` (mean 244.8 vs 154.4) and `machine_advantage` (51.2 vs
49.2), where one fast machine and long chains make precedence binding. Both are
computed and the max is taken.

**Validity check.** `LB > achieved makespan` would disprove the bound. Across all
45 generated instances and all 10 edge cases, violations: **0**.

### Effect on conclusions

All gap percentages in this document use the corrected bound. Mean greedy gap
across classes fell from ~73% to ~59%; the *ranking* of classes by gap was
largely preserved, so Failure Modes 1–4 survive the correction. Reporting the
old numbers would have systematically overstated how much headroom the
algorithms were leaving.

## Cross-cutting summary

| failure mode | trigger condition | cheapest test of the proposed fix |
|---|---|---|
| FM1 GA degenerates to greedy | dominance ratio > ~1.2 | fast-machine-biased initialization |
| FM2 greedy myopia | low flexibility, high variance | dispatching-rule portfolio |
| FM3 SLGA premature convergence | short generation budget | shrink Q-table, persist across runs |
| FM4 wasted budget | >20 generations without improvement | early-stopping criterion |
| FM5 weak lower bound | machine-constrained instances | *fixed and validated* |

The dominance ratio deserves emphasis as the main analytical contribution here:
it is measurable before running any metaheuristic, it explains four of the nine
classes' behavior with ρ = −0.70, and it reframes an apparent algorithm
weakness ("GA fails on flexible instances") as an initialization-design problem.

## Limitations

- One problem size (10 jobs × 6 machines). Conclusions about search stagnation
  may change at larger scale, where random initialization is relatively worse
  and the greedy seed may dominate even more.
- Five seeds per class. Enough to see consistent patterns (5/5 stagnation is
  unambiguous) but too few for significance testing on the small SLGA-vs-GA
  differences, which is why FM3 is stated as "no consistent advantage" rather
  than "SLGA is worse".
- The lower bound, though improved, is still loose — remaining gaps of ~50% are
  a mixture of genuine suboptimality and bound weakness, and the two cannot be
  separated without an exact solver. Adding a CP-SAT or MILP reference on small
  instances would let the true optimality gap be measured.
